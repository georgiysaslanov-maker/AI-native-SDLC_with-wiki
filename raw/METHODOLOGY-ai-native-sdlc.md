# Методика внедрения LLM-агентов в SDLC в МТС Exolve 



**Дата:** 2026-09-30 · **Статус:** draft

Методика **вендор-нейтральна**: описывает роли, контракты и контроль, а не конкретный продукт. 

---


Методика перестраивает SDLC в конвейер из 5 стадий с обратными связями (Plan → Design → Build → Test → Deploy): агент выполняет черновую работу, человек утверждает результат на явных точках контроля (gate). Каждая стадия оставляет версионируемый артефакт (`intent.md → spec.md → tasks.md → diff+tests → PR`);Старт — под контролем человека; автономия расширяется по мере созревания контроля (rules → skills → hooks → evals) и по метрикам.
Внедрение поэтапное, начиная с общего фундамента. Успех измеряется в двух слоях: наверху **бизнес-метрики** (время «идея → прод», стоимость на фичу, доля дефектов в проде), а DORA и AI-специфичные — операционные.

Узкое место смещается с написания кода на проверку и приёмку результата — отсюда упор методики на верификацию, управление контекстом и governance.

## 0.2 Ключевые решения


- **Решение 1 — доступ к модели: организационный, не персональный.** Целевой доступ — организационный: платформа владеет ключами и контролями, ввод/вывод по умолчанию не идёт в обучение. Персональный доступ (личные учётки, включая Claude Code) полезен для освоения на личных задачах, но как основа платформы не годится. Организационный доступ — предусловие Фазы 0. 
- **Решение 2 — порядок трансформации.**  Три пути — greenfield-first (пилот) / transform-first (baseline ) / два трека; 
рекомендация  **greenfield-first**, а параллельно готовить product и tech context


### Доступ к модели — организационный, не персональный (Решение 1)

Контроли периметра выше (скан ПДн, deny-правила, ограничение инструментов, атрибуция) держатся только если доступом к модели владеет **организация**, а не сотрудник. Развилка проходит не по линии «чат или агент» (агент возможен в обоих), а по линии **кто владеет доступом и управляет контролями — сотрудник или организация**. Есть два пути.

**Путь 1 — персональный доступ (личные учётки, включая Claude Code).** Полноценный агент в IDE/терминале, но контроли и управление данными живут в личной конфигурации сотрудника: платформа не может задать их централизованно, гарантировать и аудировать; нет единого логирования, идентичности агента, контроля расходов; на потребительских тарифах данные по умолчанию могут идти в обучение.  Организационно недопустимо: доступ, расходы и логи привязаны к частному лицу, а не к организации, и не контролируются платформой.

**Путь 2 — организационный доступ (Enterprise-решение).** Enterprise/Business-тариф + организационные API-ключи, которыми владеет и управляет платформа. Ввод/вывод по умолчанию **не** используется для обучения (для Anthropic — commercial-продукты и API исключены из обучения; для другого вендора нужно проверять дополнительно). Даёт админ-панель, централизованный биллинг и логирование; платформа владеет контролями (неотключаемые правила, скан ПДн, единые deny-правила), данными, телеметрией и атрибуцией, и запускает агента в CI/CD.

| Критерий | Персональный доступ (в т.ч. Claude Code) | Организационный доступ (Enterprise-решение) |
|---|---|---|
| Кто владеет контролями (hooks, permissions) | сотрудник — настраивает и отключает сам | организация — задаёт централизованно, инженер не ослабляет |
| Скан ПДн/секретов, единые deny-правила | не централизованы | на стороне платформы, для всех |
| Обучение на ваших данных | на потребительских тарифах — по умолчанию возможно | **не** используется для обучения по умолчанию (плюс Enterprise) |
| Централизованное логирование и идентичность агента | нет | есть |
| Контроль расходов и видимость токенов | нет | есть (админ-панель, лимиты) |
| Запуск агента в CI/CD | технически возможно, но не под контролем организации | да, под контролем организации |
| Что можно построить | агенты под управлением сотрудника | агенты под управлением организации |
| Соответствие этой методике | частичное (освоение на личных задачах) | полное |

**Вывод.** Личный доступ, включая Claude Code, полезен, чтобы разработчики освоили агентную работу на своих задачах в IDE/терминале — при жёстком правиле: данные клиентов, секреты и (по классификации) отдельные репозитории в личный доступ не отправляются никогда. Но как основа платформы он не годится. **Вся дальнейшая методика построена на организационном доступе (Enterprise-решение).** Переход на него — предусловие Фазы 0 (§9).

## 0.3 Главные риски 

- Весь обмен с моделью идёт через внешний API — значит, код, US и proto покидают периметр при каждом обращении; это принятый  риск, который снижаем классификацией репозиториев и использованием Enterprise-решения. Данные клиентов (ПДн, содержимое звонков и сообщений, тайна связи) агенту для разработки не нужны, поэтому не попадают в его контекст. Для чувствительных задач возможно потребуется поднятие локальных LLM.
- Ни один агент не мержит собственный код — это закрыто настройками защиты веток. Каждое действие агента логируется и привязано к запустившему его человеку.
- Блокировка Enterprise/Business аккаунта, если будет след использования из РФ.

Реестр всех рисков находится в Часть 7

# Часть 1. Главные  принципы (фундамент)



| # | Принцип | Что означает на практике |
|---|---|---|
| 1 | **Артефакт — истина и аудит** | Каждая стадия заканчивается версионируемым артефактом, который читает следующая. Цепочка коммитов отвечает на вопрос «кто что просил, что агент сделал, кто утвердил» |
| 2 | **Человек отвечает за суждение** | Агент готовит черновик; решение, требующее суждения (что построить, что смержить, что задеплоить), принимает и подписывает человек |
| 3 | **Верификация важнее генерации** | Ценность не в том, что агент пишет код, а в том, что результату можно доверять. Каждый агент обязан иметь способ проверить свою работу до того, как её увидит человек |
| 4 | **Контекст — ограниченный ресурс** | Знания загружаются точечно (just-in-time), а не «всё всем». Раздутый контекст ухудшает результат и стоит токенов |
| 5 | **Одно правило — одно место** | Факт живёт в одном файле, остальные ссылаются. Процедуры (skills) ≠ знания (rules/context) ≠ контракт (proto/spec). Дублирование расходится и устаревает |
| 6 | **Спека первична (SDD)** | Спецификация — первичный артефакт для любого изменения; код и тесты производны от неё. Объём спеки пропорционален изменению. |
| 7 | **Детерминизм там, где нельзя ошибаться** | Правило-подсказка (skill) делает нарушение редким; детерминированная проверка (hook) делает его почти невозможным. Всё, что должно держаться всегда, оборачивается в hook, а не только промптом |
| 8 | **Вендор-нейтральность** | Методика описывает роли и контракты, а не продукт. Модель и харнесс — сменяемые компоненты за слоем абстракции |
| 9 | **Автономия увеличивается через  зрелость** | Переход от подсказки к автономии происходит по метрикам, а не по дате. Автономия без созревших hook и evals не включается |

# Часть 2. Целевая операционная модель

Как устроен целевой сетап как система (детали — в подразделах ниже):

```
КОНВЕЙЕР:  Plan → Design → Build → Test → Deploy
           intent  spec    tasks   diff   PR

Рамка всего — ЛЮДИ И ПРОЦЕСС (команда-платформа · управление изменениями · Agile Lead)

обратная связь   [ Верификация: самопроверка · evals · приёмка AQA ]   [ Метрики: бизнес + DORA/AI ]
──────────────────────────────────────────────────────────────────────────────────────────────────
ядро конвейера   [ Межсервисная доставка и релиз: оркестратор + сервисы · 2 режима ]
(снизу вверх)    [ SDD-ядро в Git:  OpenSpec · polyrepo · 2 гейта · CODEOWNERS ]
                 [ LLM и агенты (L1/L2/L3):  Enterprise-доступ + шлюз · opencode · роли ]
──────────────────────────────────────────────────────────────────────────────────────────────────
ограждения       КОНТРОЛИ по жёсткости: правила/контекст → skills → hooks → платформа → gate (человек)
(поперёк всего)  + периметр данных, kill-switch
```


## 2.1 Конвейер AI-SDLC 

Пять стадий образуют конвейер с обратными связями. Каждая производит артефакт, который запускает следующую:

| Стадия | Входной артефакт | Выходной артефакт | Что фиксирует |
|---|---|---|---|
| Plan | идея / тикет | `intent.md` | что хотим, зачем, при каких ограничениях |
| Design | `intent.md` | OpenSpec: `proposal`+`specs` → `design`+`tasks` | требования + дизайн + отмеченные зоны риска (SDD-ядро) |
| Build | `design`+`tasks` | `tasks.md` (раздел «План реализации») + diff | код-обоснованный план → код |
| Test | diff + `tasks.md` | тесты + результаты evals | доказательство корректности |
| Deploy | зелёный PR | находки ревью + merge + запись релиза | ревью, gate, выкатка |



## 2.2 Вендор-нейтральная агентная архитектура

Строим слой абстракции, без привязки к продукту. Три уровня:

```
┌─────────────────────────────────────────────────────────────┐
│  L3. РОЛИ АГЕНТОВ                 │
│  orchestrator · spec · coder · reviewer  ·  etc             │
├─────────────────────────────────────────────────────────────┤
│  L2. ХАРНЕСС (сменяемый)                                     │
│  opencode / собственный оркестратор / Claude Code / …        │
│  единый интерфейс: prompt, tools, hooks, permissions, logs   │
├─────────────────────────────────────────────────────────────┤
│  L1. МОДЕЛЬ (сменяемая, внешний API — Enterprise-решение)              │
└─────────────────────────────────────────────────────────────┘
```


- **L1 — модель.** То, что отвечает на запрос. Сменяемый компонент: выбирается под задачу. К контрактам и evals не привязана — провайдера можно заменить, не переписывая роли.
- **L2 — харнесс.** Оболочка, в которой работает агент: запускает модель, даёт ей инструменты, перехватывает вызовы (hooks, permissions), пишет логи.  Здесь технически реализуется часть контролей. Сменяемый: opencode сегодня, Claude Code потенциально позже — при смене меняется только этот уровень.
- **L3 — роли агентов.** Контракты «кто за что отвечает и чем ограничен». От модели и харнесса не зависят.

**Доступ к модели и ключи.** На границе L2↔L1 стоит внутренний **шлюз** (gateway/proxy). Доступ организационный, не персональный (Решение 1, §0.2):

- **идентичность — на человека** (корпоративный SSO): нужна для атрибуции действий (R-06) и токен-бюджетов; **сырой API-ключ разработчику не выдаётся**;
- **ключи — пул из единиц, не по числу людей**: сегментация по границам риска и учёта — интерактивная разработка (1 пул) · CI по окружениям (dev/staging/prod) · служебный ключ для батч-агентов (reverse-spec). Порядок — **~3–6 ключей, не 15 и не 130**;
- **харнесс ходит на endpoint шлюза** (переопределение base URL) с короткоживущим токеном по SSO — **сырой провайдерский ключ не покидает платформу**;
- **шлюз — единая точка kill-switch и токен-бюджетов**: централизованный отзыв/ротация ключей и лимиты по командам (R-07); меньше ключей + одна точка = меньше поверхности под R-14.

Это согласует «организационный доступ» (Решение 1) с «действие привязано к человеку» (R-06): идентичность — на человека, секрет — централизован. Раздача сырых ключей по людям сломала бы Решение 1, kill-switch и периметр.

**Роли агентов** (минимальный набор на 5 стадий):

| Роль | Стадии | Что делает | Чем ограничена |
|---|---|---|---|
| **orchestrator** | все | маршрутизирует задачу, вызывает роли; знаниями сам не владеет — их подтягивает исполнитель по месту | не пишет в базу знаний |
| **spec** | Plan, Design | превращает intent и источники в `spec.md` (EARS), находит неопределённости и противоречия; читает `product-context/` по индексу за доменными фактами | открытые вопросы формулирует, но не отвечает на них сам |
| **coder** | Build | по `tasks.md` пишет код и тесты; читает правила и контекст репозитория | не мержит; не трогает защищённые пути (hook) |
| **reviewer** | Test, Deploy | ревьюит PR против политики (`REVIEW.md`), сверяет с spec и tasks | находки не утверждают PR — утверждает владелец кода через защиту веток |

**Где живут знания:**

- **Правила / контекст репозитория** (аналог `CLAUDE.md`): конвенции, команды сборки и тестов, архитектура, частые ошибки. Один файл в корне репозитория, ревьюится как код, до одной страницы, читается в начале сессии.
- **Skills**: обязательные правила организации для единообразного применения (стандарт безопасности, API-конвенции). Триггерятся по описанию, версионируются, обновляются централизованно.
- **Контекст по месту (just-in-time)**: доменные факты — выборочно по индексу, не «всё всем». 



## 2.3 Слои контроля

Контроль выстроен по возрастанию жёсткости; каждый следующий подпирает предыдущий:


| Слой | Тип | Где реализуется | Пример | Что даёт |
|---|---|---|---|---|
| **Правила / контекст** | пассивный | L3 (роли читают) | контекст репозитория, конвенции | агент знает, как надо |
| **Skills** | подсказка | L3 (роли применяют) | skill проверки безопасности API | нарушение становится редким |
| **Hooks** | детерминированный | L2 (харнесс) | блок правки защищённого пути; gate релиза | нарушение почти невозможно |
| **Настройки платформы** | неотключаемый | L2 / платформа | permissions, sandbox — задаёт платформа | инженер не может ослабить правила |
| **Точка контроля человеком (gate)** | суждение | вне стека агента | утверждение спеки, merge, авторизация релиза | ответственность на человеке |



## 2.4 Источник истины и легаси-системы 

Мы начинаем создавать новые `.md`-артефакты (intent, spec, plan). Но те же сведения уже лежат в наших системах: задачи — в Jira, тест-кейсы — в TestIT, код — в GitLab. Если одно и то же хранится в двух местах, копии со временем расходятся и никто не знает, где правда.

Предлагается: **для каждого типа артефакта выбираем одно авторитетное место — «источник истины», остальные на него ссылаются.** Три рабочих варианта:

- **Репозиторий — источник истины.** `.md`-файлы, Jira/TestIT ссылаются на коммиты. Чище всего для инженерных артефактов.
- **Легаси-система — источник истины.** Jira/TestIT авторитетны, `.md` — рабочие копии; агент читает запись в начале сессии и пишет результат обратно через коннектор в той же сессии.
- **Только перекрёстные ссылки .** У каждого `.md` есть ID записи в Jira/TestIT, у каждой записи — SHA коммита. Приняли, что источников два.

Перекрёстные ссылки — рабочая модель, и по артефактам приняты решения:
- **Требования — репозиторий** (`openspec/specs/`); Jira → трекер задач.
- **Тест-кейсы — TestIT** (агент пишет и обновляет их туда через коннектор, тест-документация — целевой артефакт), связка по `R-id` с требованиями в репозитории.
- Изменение требования через «разницу требований» (§3.1) **помечает связанные тест-кейсы TestIT на регенерацию/ревью**, а коннектор пишет обновление обратно.


## 2.5 Периметр данных и чувствительные данные

Self-hosted-моделей нет, поэтому **весь обмен с моделью идёт через внешний API**. Отсюда два разных класса данных и два разных решения.

**Инженерные артефакты — код, US, proto, spec, план, тест-кейсы.** Они нужны агенту для работы и покидают периметр при каждом вызове. 
Что делаем для снижения:
- Классифицируем репозитории: какие вообще допустимо отправлять во внешний API.
- Используем Enterprise-решение (Enterprise/Business-тариф + организационные API-ключи), где ввод/вывод по умолчанию не идёт в обучение и есть зона хранения.
- Ограничиваем набор доступных агенту инструментов и его исходящий трафик.

**Данные клиентов — ПДн абонентов, содержимое и метаданные звонков и сообщений, тайна связи, биллинг.** Для разработки они агенту не нужны: он работает с кодом и спецификациями, а не с продакшн-данными. Правило: такие данные **не попадают в контекст агента вообще.** Что делаем:
- В тест-данных и фикстурах — только синтетика или обезличенные значения. Реальные абонентские данные в US, промптах и тестах запрещены.
- Перед отправкой во внешний API diff проходит проверку на секреты и ПДн (pre-commit / CI hook). Нашли — блокируем.
- Логи и трейсы, прикладываемые к задаче, маскируем.
- Если задача действительно требует чувствительных данных — она не отдаётся агенту и остаётся ручной, пока не появится контур с моделью внутри периметра.



## 2.6 Продуктовый (доменный) контекст

- **Продуктовый контекст** — **сквозное доменное знание** (термины, типы клиентов, статусные модели, интеграции, правила тарификации), не привязанное к одному сервису; читает любой агент на любой стадии, чтобы не галлюцинировать бизнес-факты и не переоткрывать их в каждой сессии.

**Расположение.** `product-context/` 
**Структура.** `product-context/INDEX.md` (однострочные описания файлов) + доменные файлы, нарезанные по границам того, что реально нужно агентам, а не по структуре вики. Стартовый набор адаптируется под продукт — например: `glossary.md`, `client-types.md`, `lifecycle.md`, `integrations.md`, `billing-rules.md`.

**Формат файла** — frontmatter (`name`, `description`, `updated`, `owner`) + факты с обязательным источником:

```markdown
---
name: client-types
description: Типы клиентов — права доступа, ограничения операций
updated: 2026-09-04
owner: <владелец домена>
---

## Матрица прав
| Операция | Тип A | Тип B | Источник |
|---|---|---|---|
| ... | ✅ | ❌ | US EXOLVE-123 |
```

Факт без источника (US, Confluence, подтверждение эксперта) не должен попадать в файл.


**Наполнение — три источника, в указанном порядке:**

1. **Jira, разово на старте.** Агент прогоняет историю US, извлекает факты с `source: EXOLVE-XXX`.
2. **Confluence, разово на старте.** Агент прогоняет пространства, привязанные к продукту, извлекает факты с пометкой «задокументированное намерение, не проверенное поведение» — Confluence может быть устаревшим.
3. **Ручное закрытие пробелов, постоянно.** Там, где после первых двух шагов остаются явные пробелы, продукт закрывает их через тот же интервью: агент задаёт вопросы, оформляет файл, — целевой артефакт `product-context/*.md` вместо `intent.md`. 

Продукт валидирует черновик из всех трёх источников целиком, только после этого — коммит.

**Порядок наполнения зависит от пути.** Тяжёлый разовый прогон Jira/Confluence (шаги 1–2) — действие, требуемое прежде всего под путь **transform**. Поэтому в Фазе 0 и на greenfield-пути продуктовый контекст стартует **тонким** — глоссарий плюс то, что реально нужно пилоту, — набираемым через интервью Plan. Полный скан двух источников подключается вместе с transform-путём.

**Загрузка — прогрессивная, через индекс**: агент читает `INDEX.md`, выбирает 1–3 релевантных файла под задачу, не грузит слой целиком.

**Пополнение дальше.** Каждая новая принятая `spec.md` — потенциальный источник нового доменного факта: если в ней всплыло что-то за рамками одного изменения, факт выносится в `product-context/`. Открытые вопросы и допущения из `intent.md`/`spec.md`, закрытые ответом продукта, конвертируются в факты того же слоя тем же порядком.

**Владелец.** Продукт/аналитик — по домену; факт меняется через обычный MR в репозитории.

## 2.7 Масштабирование контекста

Два слоя знаний масштабируются по-разному и индексируются **разными механизмами**:

| | Продуктовый (доменный) контекст (§2.6) | Контекст репозитория (§2.2) |
|---|---|---|
| Что содержит | сквозные доменные факты (термины, статусы, тарифы) | репо-конвенции, команды сборки/тестов, архитектура, грабли |
| Индексируется | **по релевантности** — `INDEX.md`, агент выбирает 1–3 файла по теме | **по локальности** — файловая иерархия; грузится контекст того места, где идёт работа |
| Форма | библиотека доменных файлов + `INDEX.md` | корневой one-pager (≤1 стр.) + локальные `CONTEXT.md` по сервисам |
| Как грузится | прогрессивно по индексу, не весь слой | по месту: корневой + локальный для текущего каталога |

**Масштабирование:** с ростом системы растёт **общее** знание, но не всегда-загружаемый файл — рост уходит в just-in-time и декомпозированные слои (больше доменных файлов под `INDEX.md`; больше локальных `CONTEXT.md` по сервисам), которые грузятся выборочно; корневой всегда-загружаемый контекст остаётся тонким. Примеры файлов — Приложение H.

# Часть 3. SDD как ядро методики


## 3.1 Что даёт

1. **Определённый вход.** Спецификация — единая точка. Неопределённость выявыявляет  и снята до генерации.
2. **Трассируемость.** Цепочка требование → тест-кейс → код → автотест становится проверяемой, а не «на глаз». Итоговый артефакт — матрица покрытия (требования × тест-кейсы × код) генерируется автоматом.
3. **Управляемые изменения.** Изменилось требование — не переделываем всё: считаем, что именно поменялось («разница требований»), и перегенерируем только затронутые  код и ТК. Нетронутое (и ручные правки в нём) остаётся целым.

## 3.2 Фреймворк — OpenSpec

Фреймворк SDD — **OpenSpec** . Причина выбора: вендор-нейтрален (работает с 30+ инструментами, не требует своих API-ключей), также  имеет плагин под opencode.

Правила использования:
- Модель артефактов OpenSpec: каждое изменение — отдельная папка `changes/<id>/` с `proposal`, `specs`, `design`, `tasks`; принятые изменения уходят в архив. Разделение `specs/` (текущая истина) и `changes/` (предложения) даёт встроенную **разницу требований** — руками её строить не нужно.

Соответствие артефактов OpenSpec нашему конвейеру:

| Наш артефакт | OpenSpec | Владелец |
|---|---|---|
| intent (запрос на изменение) | `proposal` | продукт |
| бизнес-требования | `specs` | продукт |
| техдизайн | `design` | инженер |
| нарезка на задачи + план реализации | `tasks` | инженер |

`tasks` — **двухсостояный артефакт**: на Design это нарезка на задачи (уровень подхода, утверждается на **Гейте 2**); на Build тот же файл дополняется разделом **«План реализации»** — код-обоснованной привязкой к реальному коду (какие файлы, порядок, риски, чем доказываем; §4.3). Отдельного `plan.md` нет — план реализации живёт внутри `tasks.md`.

## 3.3 Нотация — EARS + Given/When/Then

OpenSpec задаёт структуру спеки, но не диктует, каким языком писать требования внутри.
- **EARS** (Easy Approach to Requirements Syntax) — для требований: одно атомарное предложение фиксированной формы с обязательным `source:`. Атомарность даёт правило «одно требование = минимум один тест» и машинно-разбираемые идентификаторы.
- **Given/When/Then** — для критериев приёмки: исполняемая проверка на каждое требование.


## 3.4 Истина требований — репозиторий

Источник истины требований — репозиторий (`openspec/specs/`; раскладка — Прил. H.4). Следствие: **Jira перестаёт быть хранилищем требований и становится трекером задач и статусов** — тикет ссылается на спеку, но не содержит её.

Чтобы продукт не работал с git напрямую, он пишет в репозиторий через удобную обёртку (например Opencode CLI); репозиторий при этом остаётся истиной.

## 3.5 Разделение владения и два гейта

Черновик всех артефактов пишет агент. Владение и утверждение — человеческие и **разные на двух слоях**:

| Слой | Артефакты OpenSpec | Владелец (источник + утверждает) | Нотация |
|---|---|---|---|
| Бизнес: «что и зачем» | `proposal` + `specs` | продукт (PO / аналитик) | EARS + Given/When/Then, много примеров |
| Технический: «как» | `design` + `tasks` | инженер | EARS строже + ссылки на proto |

Из разделения следуют **два гейта**, а не один:
- **Гейт 1 (бизнес-приёмка).** Продукт принимает бизнес-требования. Это вход в техдизайн.
- **Гейт 2 (техническая приёмка).** Инженер принимает `design` + `tasks`. Это вход в Build.

**Связь бизнес-спеки и техдизайна.** На переходе от бизнес-требований к техдизайну легко потерять смысл. Чтобы этого не было: каждый элемент техдизайна ссылается на конкретное бизнес-требование (R-id); если бизнес-требование, US и proto противоречат друг другу, агент останавливается и задаёт вопрос владельцу, а не выбирает вариант сам.

## 3.6 SDD применяется ко всем изменениям

Через спеку проходит **любое** изменение.  **Объём спеки пропорционален изменению**: тривиальное (добавить поле, поправить лог) — 1–2 требования EARS и один критерий приёмки, агент генерирует быстро, человек утверждает без углублённого разбора; нетривиальное — полная спека с дизайном и разбором противоречий.

**Спека-артефакт — для всех; продуктовый гейт — не для всех.** Требование «спека на любое изменение» держит трассируемость, но не означает, что каждое изменение проходит через приёмку продуктологов. Иначе 100% изменений маршрутизируются через самый дефицитный ресурс (~20 человек), и lead time для массы мелочей будет расти. Поэтому класс изменения решает, нужен ли Гейт 1:
- **Меняется внешне наблюдаемое бизнес-поведение** (новое поле в ответе, новое правило тарификации) → Гейт 1 продуктологов обязателен. Изменение `proto` / публичного контракта — автоматический триггер Гейта 1.
- **Нет внешне наблюдаемого изменения** (рефакторинг, внутренний техдолг, логи, производительность) → спека остаётся, но `proposal` + `specs` владеет и принимает **инженер**; продуктовый гейт не нужен. Здесь Гейт 2 (техприёмка) — единственный. В OpenSpec маленькое изменение — это маленькая папка `changes/<id>/`.
 Пример минимальной спеки:

```
proposal: добавить булево поле `call_record` в объект `attributes` ответа GetAttributes

specs:
  R-1 [Event-driven]: КОГДА вызван POST /number/v1/GetAttributes с валидным `number_code`,
      СИСТЕМА ДОЛЖНА вернуть в объекте `attributes` булево поле `call_record`.
      source: proposal

  AC-1 (R-1):
    Given номер существует и запись разговоров выключена,
    When  POST https://api.exolve.ru/number/v1/GetAttributes
          body {"number_code": "<code>"},
    Then  ответ 200, attributes.call_record = false.

  AC-2 (R-1):
    Given номер существует и запись разговоров включена,
    When  тот же вызов,
    Then  ответ 200, attributes.call_record = true.
```

## 3.7 Поток для нового кода (greenfield)

`intent` → бизнес-спека (продукт, **гейт 1**) → техдизайн + `tasks` (инженер, **гейт 2**) → Build.

## 3.8 Поток для легаси (reverse-spec)

Важно: Агент не может безопасно менять код, поведение которого нигде не описано. Поэтому для легаси сначала  нужно снять **baseline** — спеку «как есть» поверх существующего сервиса, — и только потом менять. Baseline — это поведение одного сервиса под конкретное изменение; сквозное доменное знание (термины, статусные модели, типы клиентов) живёт отдельно, в продуктовом контексте.

**Источники и их приоритет.** Baseline снимается из трёх источников с жёстким приоритетом; расхождения  нужно разбирать:

| Источник | Роль | Приоритет |
|---|---|---|
| Код | что система фактически делает — истина | высший |
| Тест-кейсы | вторичный сигнал; описывают, как тестировали, а не как работает | средний |
| Confluence | задокументированное намерение («зачем»), не доказательство поведения | низший |

Confluence у нас структурирован и привязан к сервисам, поэтому агенту подаётся только пространство нужного сервиса, а не всё подряд. Ценность Confluence — не в снятии поведения, а в подсказке для бизнес-вопроса: он вскрывает **расхождения код↔Confluence** (поведение разошлось с намерением —  сигнал для продукта). Флагами поднимаются все три вида расхождений: код↔тесты, код↔Confluence, Confluence↔тесты. 


**Уровни уверенности.** Каждое снятое поведение агент помечает уверенностью, чтобы валидация инженера была содержательной, а не формальной:

| Уровень | Основание | Внимание инженера |
|---|---|---|
| высокая | подтверждено и кодом, и тестом | беглое |
| средняя | выведено только из кода, теста нет | обязательное |
| низкая | источники противоречат друг другу | приоритетное |

**Цепочка:**

reverse-spec агент (скилл «снять поведение», приоритет код > тесты > Confluence) → черновик baseline с пометками поведения, уверенности и расхождений → **инженер валидирует** технику и флаги, фокус на среднем/низком доверии → агент **переформулирует** каждое правило в бизнес-вопрос («система при X делает Y — это намеренное правило, баг или устаревшее?») → **продукт выносит вердикты**, глубина зависит от класса критичности сервиса → baseline принята (ложится в `openspec/specs/<сервис>/`, раскладка — Прил. H.4) → дальше обычный поток на изменение.

**Глубина продуктовой валидации — по классу критичности** (опираемся на существующую классификацию сервисов):
- критичные сервисы (биллинг, тарификация, тайна связи) — продукт проходит по каждому правилу вдумчиво
- некритичные (внутренние сервисы) — выборочное подтверждение, без сплошного разбора.

**Роли и скиллы.** На старте это один reverse-spec агент с двумя скиллами (снять поведение / перевести поведение в бизнес-вопросы). Качество второго скилла определяет, сможет ли продукт вообще участвовать. Поэтому оно проверяется на reverse-spec-образце Фазы 0. Критерий — продукт реально смог вынести вердикты по сгенерированным бизнес-вопросам. 

**Запасной план, если скилл слаб.** Если reverse-spec-образец Фазы 0 показал, что продукт не может выносить вердикты по бизнес-вопросам (no-go, §9.1), легаси-путь **не разворачивают вширь**, а переходят к запасному варианту: сузить reverse-spec (меньший объём на сервис, больше человека в контуре) **или** осознанно оставить легаси ручным дольше, пока скилл не дозреет. Решение принимается на данных одного сервиса, а не обнаруживается сюрпризом на 40-м.

**Владение документацией.** Вердикт «документация устарела» порождает задачу на обновление страницы Confluence, которую закрывает владелец сервиса. Иначе reverse-spec будет находить одно и то же расхождение на каждом прогоне.

## 3.9 Утверждение и трассируемость

Гейты — по §3.5 (человек, не агент). Итоговый артефакт трассируемости — матрица покрытия (требование × тест-кейс × код). Требование без `source` не принимается. Матрица сшивается через `R-id` ↔ TestIT-id (тест-кейсы живут в TestIT, требования — в репозитории), охватывая оба хранилища; изменение требования флагует связанные тест-кейсы TestIT.

- **Хранение:** матрица не ведётся руками — это **генерируемый в CI отчёт** (join `R-id` ↔ кейс TestIT ↔ автотест по номеру TC; код `R-id` не несёт). Источники версионируются (спеки — в git, кейсы — в TestIT); матрица прикладывается к PR и/или на дашборд, снапшот — на релиз для аудита.
- **Роль человека:** не строит, а **читает как сигнал** на гейте (есть ли дыры, приемлем ли радиус изменения) и решает по дыре (принять / завести тест); единственная ручная валидация — легаси-сопоставление `R-id` ↔ кейс TestIT.
- **Этап:** рождается на **Design** (`R-id` + `source`), наполняется на **Test**, служит **гейтом на Deploy** (элемент DoD).



## 3.10 Антипаттерны

- Спеку и пишет, и утверждает агент —  галлюцинацию (R-01). Черновик — агент, утверждение — человек.
- Инженер подтверждает baseline целиком, без разбора; внимание должно идти на среднее и низкое доверие и на флаги.
- Продукту показывают техническое описание поведения вместо бизнес-вопроса — продукт не может дать вердикт и выпадает из процесса.
- Три источника слиты в гладкую спеку — спрятаны противоречия, ради которых reverse-spec затевался.
- Требования продублированы в Jira и в спеке — копии расходятся; требования живут только в спеке, тикет ссылается.


## 3.11 Межсервисные изменения

Фича часто трогает **много сервисов через оркестрирующий сервис продуктового слоя**. Пример: публичный метод `sip/v1/Create` на оркестраторе (NGW/WEB) вызывает ~7 нижележащих сервисов (RI, NMS, Product Offering, CMA, Billing, Voice Cluster, Action History), каждый — своя команда. Единого «тех-лида на фичу» нет; модель остаётся SDD.

**Два слоя.** Продуктовый слой — оркестрирующий сервис (напр. NGW) + WEB: владеет публичным методом (клиентский API) и собирает поведение end-to-end. Нижележащие сервисы — каждый своя команда, свой внутренний контракт.

**Два уровня контракта (contract-first на обоих).**
- **Публичный контракт** (клиентский метод; REST-спека + proto) — внешне наблюдаемая поверхность. **К нему привязан Гейт 1 (бизнес)** — один на фичу (§3.6); владеют продукт + команда оркестратора.
- **Внутренние контракты** (оркестратор → нижележащий сервис; proto/gRPC) — **к ним привязаны пер-сервисные Гейты 2 (техника)**, каждый у своей команды.
- Гейт 1 срабатывает на изменение **публичного** метода/поведения, независимо от того, какой слой его инициировал. Обратно совместимое изменение нижележащего сервиса, не меняющее публичный метод, → только его Гейт 2.
- Контракт (публичный или внутренний) не ломается в одностороннем порядке — только через версионирование и координацию через оркестратора.

**Владение (тех-лида на фичу нет).**
- Каждый нижележащий сервис владеет своей частью: свой `changes/<id>/` (ссылается на контракт и фиче-R-id), свой Гейт 2, свои тесты, свой релиз.
- **Интегратор фичи — команда оркестратора** (NGW/WEB): владеет публичным методом, собирает и тестит связку **E2E**, делает клиентский релиз.
- Бизнес-готовность user story — на PO (Гейт 1).

**Релиз — два режима.**
- **По умолчанию — независимый.** Внутренний контракт обратно совместим → каждый нижележащий сервис деплоит сам после своего Гейта 2, своих тестов и проверки обратной совместимости контракта (proto breaking-change). **Выкладка кода в прод и включение фичи клиенту — разные события:** части (и даже новый публичный метод) можно выложить в прод заранее, но держать **выключенными для клиента** (feature-флаг или просто не публикуя метод). **Клиенту публичный метод становится доступен только после зелёного E2E-теста у оркестратора.**
- **Cараллельный (синхронный).** Когда обратная совместимость невозможна или нет безопасного промежуточного состояния: части выезжают в одном согласованном окне вместе, с **согласованным откатом**; окно координирует команда оркестратора. По умолчанию стремимся к обратной совместимости, чтобы синхронный режим был редким.

**Покрытие — двухуровневое.**
- Пер-сервисная матрица (§3.9) — у каждой команды: R-id сервиса ↔ кейс TestIT ↔ автотест.
- Фиче-уровневое (E2E) покрытие — у команды оркестратора: публичный R-id фичи ↔ E2E-кейс ↔ E2E-автотест; проверяется перед публичным релизом.
- Склейка по фиче-R-id; единой «мегаматрицы» по всем внутренностям фичи нет.

**Рабочий пример: межсервисная фича от интента до клиента.**
*Фича:* в ответ `sip/v1/Create` добавить поле `sip_remaining` — сколько SIP ещё можно создать по тарифу. Трогает NGW (оркестратор), Product Offering (лимит по тарифу), RI (текущее количество), WEB.

1. **Plan.** PO описывает интент через OpenCode-пресет; интент один на фичу, про публичный метод, ложится в репозиторий оркестратора (NGW). PO утверждает.
2. **Design.** Агент разворачивает бизнес-спеку публичного метода (новое поле + критерии приёмки) → **Гейт 1 (продукт)**. **Разбор по слоям** — определить, какие сервисы и что предоставляют (Product Offering — лимит по тарифу, RI — текущее количество, NGW — сборку, WEB — показ) — **координирует команда оркестратора** (владеет публичным методом и знает весь сиквенс); но дизайн своей части пишет каждая команда сама. Каждая затронутая команда (Product Offering, RI, NGW, WEB) заводит свой `changes/<id>/` со ссылкой на фиче-R-id и внутренний контракт → **пер-сервисный Гейт 2**. Контракты согласуются contract-first (добавление поля — обратно совместимо).
3. **Build.** Каждая команда пишет свою часть в своём репозитории (параллельно/последовательно): Product Offering отдаёт лимит, RI отдаёт количество, NGW собирает и кладёт поле за флагом, WEB показывает.
4. **Test.** Каждый сервис — самопроверка + свои тесты + проверка обратной совместимости контракта. Оркестратор — E2E всей связки `Create` с новым полем.
5. **Deploy.** Нижележащие — **Product Offering и RI** — катятся в прод независимо (обратно совместимо); **NGW** выкладывается со сборкой, но поле выключено для клиента (флаг). Когда все части в проде и **E2E зелёный — команда оркестратора (NGW) включает поле клиенту**.
6. **Покрытие.** Каждая команда — своя матрица; оркестратор — фиче-E2E покрытие публичного R-id; склейка по фиче-R-id.


## 3.12 Раскладка в polyrepo (группа GitLab)

Продукт — **100+ микросервисов в группе GitLab, не монорепа**. 

```
группа GitLab: git.<...>/<группа>/
├── numbers-service/          ← сервис = репозиторий
│   ├── openspec/
│   │   ├── specs/            ← истина требований сервиса (+ baseline легаси, §3.8)
│   │   └── changes/<id>/     ← proposal / specs / design / tasks
│   ├── <код сервиса>
│   └── CONTEXT.md            ← подсказки агенту по локальности (§2.2)
├── billing-service/   …  (аналогично)                     × 100+
├── contracts/                ← общие proto — контракт межсервисных (§3.11)
└── product-context/          ← доменный контекст + INDEX.md (§2.6)

```

- **`openspec/` — в каждом репозитории сервиса.** `specs/` (истина требований сервиса) + `changes/<id>/`. Владение, CODEOWNERS, гейты — пер-сервисные. Baseline легаси (reverse-spec, §3.8) ложится в `openspec/specs/` того же репозитория.
- **Общее — в отдельных репозиториях группы** (не дублируем в 100+ репо): **`contracts/`** (общие proto — контракт межсервисных изменений) и **`product-context/`** (доменный контекст, §2.6; агент читает его поверх сервисного).
- **Неймспейс R-id: `<сервис>/R-<n>`** (`numbers/R-1`, `billing/R-1`). TestIT один на всю группу → R-id должен быть глобально уникален. Матрица покрытия (§3.9) по умолчанию **пер-сервисная**; при необходимости агрегируется по префиксу.
- **Межсервисная фича — по §3.11:** contract-first на двух уровнях (публичный контракт → Гейт 1; внутренние → пер-сервисные Гейты 2); тех-лида на фичу нет — интеграция и E2E на команде оркестратора; релиз в двух режимах (независимый по умолчанию / синхронный как исключение).
- **Единообразие раскатывает платформа:** единый шаблон `openspec/` + CODEOWNERS + защита веток разворачиваются по репозиториям группы централизованно (Фаза 0), а не заводятся руками в каждом.

# Часть 4. Стадии (plays)

## 4.0 Механика передачи между стадиями

Стадии передают эстафету не «по волшебству» — механизм конкретен и переиспользует git и трекер, без нового тулинга.

**Три носителя сигнала.**
- **Git — истина и гейт.** Артефакт каждой стадии (`intent.md` → `spec` → `design`+`tasks` → diff → PR) живёт в репозитории и передаётся следующей стадии как есть. Сигнал «пора утверждать» несёт **MR + CODEOWNERS**: запрос ревью автоматически маршрутизируется на нужного человека — это и есть уведомление о гейте. Merge = переход на следующую стадию.
- **Jira — зеркало статуса.** Тикет отражает, на какой стадии изменение и на кого назначено — для планирования и видимости; двигается коннектором вслед за git, но истиной не является (§3.4).
- **Orchestrator — маршрутизация внутри сессии.** Внутри одной стадии оркестратор вызывает нужную роль (`spec`, `coder`, `reviewer`) и подтягивает контекст по месту. Эстафету между стадиями и людьми он **не** несёт — это делают git и гейты.

**Два типа передачи — не путать.**
- **Внутри стадии (агентная, быстрая):** `intent` → черновик спеки делает `spec`; план реализации в `tasks` → код делает `coder`. Без человека на каждом шаге.
- **Между стадиями (человеческий гейт):** переход возможен только через утверждение человеком. Технически гейт = запрос ревью MR + защита веток; **кого спрашивают — решает CODEOWNERS по пути файла**: бизнес-спека (`proposal`/`specs`) → продукт (**гейт 1**), техдизайн (`design`/`tasks`) → инженер (**гейт 2**), код → владелец кода (merge).

**Обобщённый цикл — один и тот же на каждой стадии:**

```
   ┌──────────────────────── повтор на каждой стадии ────────────────────────┐
   ▼                                                                          │
 артефакт ──▶ MR ──▶ CODEOWNERS ──▶ ГЕЙТ ──▶ merge ──▶ следующая стадия ──────┘
  (в git)   (агент)  (маршрут       (человек
                      ревью          утверждает)
                      владельцу)

 параллельно:  git ──▶ Jira   (зеркало: статус + назначение; синхрон git → Jira)
```

**Как это выглядит на одном проходе (greenfield):**
1. Продукт закоммитил и утвердил `intent/example_intent.md` — merge. *(старт: человек; со зрелостью — CI-hook на merge)*
   → *Jira:* коннектор создаёт/связывает тикет с `intent` (по ID/SHA) и ставит статус «Design».
2. `spec`-агент разворачивает `intent` в `proposal`+`specs`, оформляет MR. CODEOWNERS шлёт запрос ревью **продукту** → **гейт 1** (продукт валидирует через OpenCode-пресет с человекочитаемой спекой, не через raw git, §10.3), merge.
   → *Jira:* тикет назначен на продукт, статус «бизнес-приёмка»; после merge гейта 1 — снят с продукта.
3. `spec`/`coder` строит `design`+`tasks`, оформляет MR. CODEOWNERS шлёт запрос ревью **инженеру** → **гейт 2**, merge = вход в Build.
   → *Jira:* тикет назначен на инженера, статус «техприёмка»; после merge — статус «Build».
4. Build → Test → Deploy идут тем же порядком: артефакт → MR → нужный человек по CODEOWNERS → гейт.
   → *Jira:* статус двигается Build → Test → Deploy; прод-деплой отражается как «ожидает авторизации релиза» (gate-hook «спросить», §4.5).

**Направление синхронизации — всегда git → Jira.** Коннектор двигает статус и назначение вслед за git-событиями (merge, запрос ревью), а не наоборот. Jira показывает, «где изменение и на ком», но истина — репозиторий (§3.4); при расхождении прав репозиторий.

**Автономия эстафеты (принцип 9).** На старте следующую стадию **запускает человек** (взял тикет, открыл сессию). По мере зрелости запуск черновика следующей стадии вешается на **CI-hook** (событие merge предыдущего артефакта), а человек остаётся только на гейтах. Триггер эволюционирует от ручного к событийному — гейты остаются человеческими.

## 4.1 PLAN 

**Что меняется.** Раньше идея проходила через backlog, оценки и refinement, теряя авторский смысл на каждой передаче. Теперь автор идеи обсуждает её с агентом и фиксирует результат как `intent.md` в своих терминах.

**Артефакт:** `intent.md` — проблема, предлагаемый исход, затронутые пользователи и системы, ограничения, открытые вопросы (шаблон — TBD).

**Как исполнять.**
1. Автор  описывает проблему агенту своими словами.
2. Агент задаёт вопросы аналитика: границы, пользователи, ограничения, критерий успеха.
3. Агент оформляет `intent.md` по шаблону (шаблон оформлен как skill).
4. Автор правит то, что агент понял неверно.
5. Коммит в общий версионируемый каталог `intent/` в репозитории продукта.

**Gate и автономия.** Утверждает владелец по классу изменения (§3.6): бизнес-изменение → продукт-оунер (Гейт 1); чисто техническое (рефактор/техдолг) → инженер. Merge фиксирует решение. Автономии на старте нет — вход всегда человеческий.

**Метрика.** Ведущая: время от первого разговора до закоммиченного `intent.md`. Отложенная: доля `intent.md`, принятых в Design, а не закрытых; число правок intent после первого `spec.md`.

**Антипаттерны.**
- Интент пишет не автор идеи, а посредник — при пересказе теряется исходный смысл.
- Шаблон заполнен формально, реальная проблема не описана — следующая стадия работает вслепую.

## 4.2 DESIGN — требования и дизайн (SDD)

Стадия целиком построена на SDD; (фреймворк OpenSpec, нотация, разделение владения, потоки greenfield и legacy).

**Что меняется.** Раньше требования и дизайн — две фазы двух команд. Теперь агент разворачивает `intent` в спеку, а владение разделено: продукт отвечает за бизнес-требования, инженер — за техдизайн. Оба черновика пишет агент, ограниченный skills (безопасность, комплаенс, UX), и явно отмечает зоны риска.

**Артефакт:** папка изменения OpenSpec — `proposal` + `specs` (бизнес, владелец — продукт) и `design` + `tasks` (техника, владелец — инженер). Требования — EARS, приёмка — Given/When/Then (шаблон TBD).

**Как исполнять.**
1. Для легаси — сначала reverse-spec: снять baseline поведения (§3.8).
2. Продукт с агентом разворачивает `intent` в бизнес-спеку; агент отмечает зоны риска и противоречия источников.
3. **Гейт 1 (бизнес-приёмка):** продукт принимает бизнес-требования.
4. Инженер с агентом строит техдизайн; каждый элемент ссылается на бизнес-требование (R-id); конфликты US ↔ proto ↔ требование — стоп-вопрос.
5. **Гейт 2 (техническая приёмка):** инженер принимает `design` + `tasks`. Это вход в Build.

**Gate и автономия.** Два человеческих гейта; утверждает человек, не агент. Автономии на старте нет; по мере зрелости черновик идёт без пошаговых подтверждений, но оба гейта остаются человеческими.

**Метрика.** Ведущая: время `intent` → принятая спека. Отложенная: доработка требований после старта Build.

**Антипаттерны.**
- Спека переписывает контракт: proto остаётся истиной , спека описывает поведение и бизнес-правила. При конфликте — агент останавливается и задаёт вопрос.
- Требование без указания источника — через месяц никто не вспомнит, откуда оно и верно ли ещё.
- Техдизайн не ссылается на бизнес-требование — связь «что» и «как» потеряна.

## 4.3 BUILD — план и реализация

**Что меняется.** Раньше инженер читал дизайн и начинал писать код; «как именно» жило в голове, и первое, что видел ревьюер, — готовый diff. Теперь Build начинается с письменного плана реализации: агент в режиме планирования читает кодовую базу, ничего не меняя, и **дополняет `tasks.md`** разделом «План реализации» (какие файлы, порядок, риски, чем доказываем); инженер правит его до написания кода.

**Артефакт:** `tasks.md`, дополненный разделом **«План реализации»** (Приложение C) → diff + тесты. Отдельного `plan.md` нет: план реализации — это код-обоснованное расширение утверждённой на Гейте 2 нарезки, а не второй документ.

**Как исполнять.**
1. Сессия в режиме планирования; на входе `design` + `tasks` (то, что утверждено на Гейте 2).
2. Запросить план реализации: какие файлы меняются, в каком порядке, какие тесты это докажут — агент дописывает это в `tasks.md`.
3. Разобрать план: что может сломаться, какой шаг рискованнее всего, какие альтернативы отвергнуты и почему.
4. Итерировать, пока по плану смог бы реализовать другой инженер.
5. Коммит обновлённого `tasks.md`, затем реализация (при хорошем плане часто в один проход). Отклонение от плана фиксируется правкой `tasks.md` в том же коммите; для этого может повести hook.

```
BUILD:  [А] агент   [Ч] человек   ══ plan mode (агент читает код, НЕ пишет)

  design+tasks (Гейт 2 пройден)
        │
        ▼
  ══════ PLAN MODE ══════════════════════════════
   [А] читает кодовую базу, дополняет tasks.md
       разделом «План реализации» (файлы, порядок,
       риски, чем доказываем)
        │
        ▼
  ┌─────────────────────────────────────────────┐
  │ ЧЕКПОИНТ ПЛАНА [Ч] — НЕ гейт (нет merge)      │
  │ «агент понял? радиус приемлем?»               │
  │   не ок ─▶ правит план (кода ещё нет) ─┐      │
  │   ◀────────────────────────────────────┘      │
  │   ок ─────────────────────────────────┐       │
  └────────────────────────────────────────┼──────┘
                                           ▼
                          [А] пишет код+тесты по плану ─▶ diff → TEST

  Зрелость: для рутины [Ч]-чекпоинт отключается (автономия по метрикам).
```

**Gate и автономия.** Утверждение плана реализации — **внутри-Build чекпоинт, не третий гейт**: инженер утверждает дополненный `tasks.md` до генерации кода (Гейт 2 на `design`+`tasks` уже пройден на Design). По мере созревания контроля (контекст репозитория, skills, hooks, тест-набор) для рутинных задач включается автоматический режим: инженер утверждает план, агент применяет правки без подтверждения каждого шага, а внимание человека смещается на проверку итогового артефакта. 

**Метрика.** Ведущая: доля изменений, влитых с первого прохода; время от утверждения плана до merge. Отложенная: число циклов доработки на изменение; насколько итоговый diff совпадает с планом реализации в `tasks.md`.

**Антипаттерны.**
- Код пишется без утверждённого плана — ревьюер впервые видит замысел уже в готовом diff.
- Знания зашиты в промпты агентов — файлы ролей должны содержать только роль и маршрутизацию, а не доменные факты.
- Контекст репозитория раздут — релевантное теряется среди устаревшего, растёт расход токенов без пользы.

## 4.4 TEST — самопроверка и непрерывные evals

**Что меняется.** Раньше сигнал  приходил от  CI, тестировщика, прод зоны. Теперь каждая сессия проверяет свою работу до человека, а конфигурация/поведение агента регрессионно тестируется, как код (evals).

**Артефакт:** тесты + результаты evals (пройденные проверки приложены к PR).

**Как исполнять — контур самопроверки.**
1. Свернуть проверку в одну команду (`make test`), возвращающую ненулевой код при провале; пример корректного вывода описать в контексте репозитория.
2. Дать агенту измеримую цель: «все тесты в X зелёные», «скриншот совпадает с макетом», «эндпоинт возвращает 200 с новым полем».
3. Для багфиксов — сначала падающий тест: агент воспроизводит баг тестом, коммитит его, затем чинит код, не трогая тест (hook запрещает правку тест-файлов в задаче на исправление). Тест, существовавший до фикса и неизменяемый агентом, доказывает, что баг ушёл.
4. Верификация — часть определения «готово»: прогнать тесты и показать вывод до отчёта о завершении.


**Как исполнять — непрерывные evals (аналог стадийного QA-гейта).**
1. Собрать 20–50 реальных задач с принятым исходом.
2. Оформить каждую как eval: промпт плюс проверки (тесты зелёные, линтер чист, поведение не изменилось, политика соблюдена).
3. Набор гоняется в CI по расписанию и на любое изменение конфигурации агента (контекст репозитория, skills, hooks) — она управляет агентом и требует постоянных проверок, как код.
4. Изменение конфигурации, роняющее pass-rate, ревьюится до merge.
5. Прод-инцидент, вызванный работой агента (дефектный код/спека, пропущенный класс ошибки), добавляется в набор evals как постоянный регресс.

**Независимый приёмочный слой — не всё отдаём LLM.** Критический смоук/приёмочный слой пишет и поддерживает человек (AQA), выводя его из Given/When/Then; этот слой недоступен агенту-кодеру (hook) и служит независимым  уровнем проверки. LLM-сгенерированные проверки добавляют охват поверх, но не заменяют человеческую проверку.

**Gate и автономия.** Верификацию-перед-готовностью и запрет правки тестов в задаче на исправление реализуем как hooks там, где нужна гарантия. Доказательство — вывод `make test` или скриншот-сравнение, приложенные к PR. Утверждает владелец кода в PR.

**Метрика.** Ведущая: доля агентных изменений, проходящих CI с первого раза; pass-rate evals во времени; время «инцидент → постоянный eval». Отложенная: время ревью на PR (должно падать); частота отказов изменений (CFR); регрессии, пойманные в CI против пойманных в проде.

**Антипаттерны.**
- Агент, который чинит код, может ослабить проверку этого кода, переписав тест.
- Evals собрали один раз и забыли — набор нужно поддерживать: устаревшие кейсы убирают, новые добавляют по результатам наблюдений.

## 4.5 DEPLOY — двунаправленное ревью и gate

**Что меняется.**  PR ждал ревьюера, качество плавало с нагрузкой. Теперь все PR получают одинаковый набор проверок (агент ревьюит входящие PR и отрабатывает комментарии на своих), а человек поднимается на уровень «делает ли изменение то, что задумано, и приемлем ли риск».

**Артефакт:** находки ревью + merge + запись релиза (подшиваются к тому же PR).

**Как исполнять.**
1. Тех-лид пишет политику ревью `REVIEW.md`: проходы (баги и логика; безопасность и уязвимости; соответствие `spec.md`, `tasks.md` и дизайн-принципам), что считается важным, а что — мелочью, что пропускать (шаблон TBD).
2. **Агент советует — мержит человек.** Комментарии агента — рекомендации: сами по себе не утверждают и не блокируют PR. Влить код можно только с апрувом живого владельца кода — держит защита веток.
3. **Правка по просьбе, всё в треде.** Человек отмечает агента в комментарии — агент вносит правку и пушит в тот же PR. В треде остаётся и запрос, и что именно агент изменил.
4. **Повторное замечание становится правилом.** Если одно замечание всплывает второй раз — его записывают в контекст/правила репозитория, и со следующего PR агент ловит это сам. Ревью обучает систему.
5. **Ежемесячная калибровка ревью**. Тех-лид пересматривает находки за период, снижает долю незначительных замечаний и выводит из-под ревью то, что не требует ручной проверки.

**Ревью и защита веток .**
- *Ревью-процесс* у нас есть: минимум один аппрув. В AI-native он становится двунаправленным — агент и даёт, и получает ревью, человек фокусируется на замысле и риске.
- *Ревьюер сильнее исполнителя.* Код, сгенерированный более дешёвой/быстрой моделью, ревьюит модель более сильного класса — она ловит другие классы ошибок, чем автор. Разрыв в силе модели между генерацией и ревью — часть контроля качества, а не только человеческий аппрув.
- *Защита веток* — настройки GitLab, не дающие смержить в защищённую ветку без выполнения условий. Это технический  строгое правило «агент действует до gate, но не за него».
- **Принятый стандарт (GitLab):** ветка `main` защищена; прямой push запрещён; обязателен минимум один аппрув владельца кода-человека (через CODEOWNERS); обязателен зелёный pipeline; всё, что пишет агент, приходит только как MR — прямого пути в `main` у агента нет; агент действует под собственной идентичностью, чтобы в логах pipeline его действия отделялись от действий инженера.

**Gate и автономия.** Разделение полномочий: агент, написавший код, не имеет способа его утвердить. Gate релиза — hook типа «спросить»: прод-деплой блокируется, пока назначенный владелец не авторизует (функция авторизации релиза на существующем владельце кода/тимлиде, не новая ставка). Автономию распределяем по окружениям: в dev агент деплоит свободно; в staging — автономно, но за автопроверкой (зелёный pipeline и прошедшие evals), без ручной авторизации; в prod агент готовит релиз, а авторизует человек, и hook это проверяет. Конкретный порог для staging калибруется по метрикам зрелости (принцип 9).

**Метрика.** Ведущая: время до первого ревью (до минут); доля комментариев, закрытых без касания ветки человеком; время ожидания на каждом gate. Отложенная: дефекты и уязвимости, пойманные до merge против ушедших в прод; DORA (частота деплоев, lead time, CFR).

**Антипаттерны.**
- Находки агента автоматически мержат или блокируют PR — человек убран из петли, ответственность размывается.
- У агента есть прямой путь в `main` — теряется разделение полномочий.
- Поток мелких замечаний топит важные — ревью перестают читать.

# Часть 5. Governance, безопасность, ответственность

Governance по AI у нас нет — создаём его как часть методики. Ниже — минимальный набор документов и технических контролей.

## 5.1 Политика использования AI (создать)

Каждый документ версионируется, у каждого — назначенный владелец:
- **Что можно и нельзя отправлять во внешний API** — правила по данным (§2.5). Обязательна к прочтению всеми.
- **Реестр обязательных правил, оформленных как skills и hooks** — единый список того, что применяется одинаково во всех командах (например: секреты не логировать, внешний API проходит проверку безопасности, merge в main только с аппрувом); у каждого правила — ответственный владелец.
- **Правила атрибуции**: каждое действие агента привязано к человеку, который его запустил.
- **Стартовый каталог инженерных политик** (оформляются как skills/hooks, §2.2) — не изобретаем с нуля, типовой набор: обработка ошибок; стандарты тестирования; дизайн API (конвенции JSON/URL); здоровье кода (лимиты на размер файла/функции); бюджеты производительности (p95, LCP); безопасность (middleware на новых эндпоинтах); дизайн-принципы фронта; структура модулей; формат задач и TDD. Каждая политика — документ с владельцем, **подпёртый контролем** (линтер / CI / hook / ревью-промпт), а не просто текст.
- **Централизованная остановка/отзыв (kill-switch).** Платформа владеет ключами и доступом (§0.2) → может немедленно отозвать доступ агента, заглушить его в CI и остановить массовые действия. Триггеры срабатывания (аномальный объём изменений, всплеск отклонений на ревью/evals, инцидент безопасности) — часть политики.



## 5.2 Аудируемость

Артефакт-цепочка служит аудиторским следом (кто просил, что агент сделал, кто утвердил — в git-истории). Дополнительно: сессии агентов логируются (экспорт телеметрии в наш стек — Prometheus / Grafana / Keep), решения hooks пишутся с временной меткой и вердиктом (пропустить / спросить / заблокировать).

## 5.3 Вендор и стоимость

- **Зависимость от вендора** снижается слоем абстракции : модель и харнесс сменяемы, evals не привязаны к одному провайдеру.
- **Стоимость обращений к модели** — данных пока нет . До получения данных: лимиты расходов на бэкенды, бюджет на прогоны evals, мониторинг токенов по командам.
- **Маршрутизация по стоимости.** Класс модели выбирается под задачу: дешёвая/быстрая — на высокообъёмную механику (реализация по спеке, рутинные правки), сильная/дорогая — на рассуждение, дизайн и ревью. Структура затрат встроена в процесс, а не наблюдается постфактум. Конкретная раскладка появляется с выбором субстрата (§11) и данными токен-экономики Фазы 0.

# Часть 6. Измерение

Под AI-SDLC заводим отдельную телеметрию. Baseline снимаем до старта, дальше сравниваем по фазам.

**Два слоя метрик.** 
-  **Бизнес-метрики** :— **время «идея → прод»**· **стоимость на поставленную фичу/изменение** · **доля дефектов в проде**.
— **Операционные метрики**: DORA и AI-специфичные метрики.


**Операционные метрики:**

| Группа | Метрика | Источник | Тип |
|---|---|---|---|
| **DORA** | Lead time for changes | GitLab / Argo | результат |
| | Deployment frequency | Argo CD | результат |
| | Change failure rate — на старте прокси **rollback/hotfix-rate** | деплой-история (Argo); incident-лог → CFR позже | страховочная |
| | MTTR | трекер инцидентов | страховочная |
| **AI-специфичные** | Доля изменений, влитых с первого прохода | метаданные PR | скорость |
| | Pass-rate evals (конфигурация агента) | набор evals в CI | качество |
| | Время до первого ревью | метаданные PR | поток |
| | Время ревью на PR | метаданные PR | поток |
| | Доля автономных действий за gate без касания человеком | логи телеметрии | зрелость |
| | Циклы доработки на изменение | история PR | качество |
| **Страховочные** | Доля дефектов в проде / escape rate (**baseline есть**) + абсолют | существующий учёт дефектов | качество (основной противовес) |
| | Находки безопасности (до merge против прода) | ревью / сканы | безопасность |
| | Стоимость обращений к модели на смерженное изменение | биллинг бэкендов | стоимость |

**Baseline и цели .** DORA сегодня не измеряется: до старта реально снимаются **lead time и deployment frequency** (метрики скорости) и текущее время ревью. 
**Доля дефектов в проде (defect escape rate): по ней baseline существует давно**.
**Change-failure**  на старте можно замерять через  **прокси — rollback/hotfix-rate** (из деплой-истории), дальнейшее развитие возможно вместо с развитием инцидент менджемента.

**Метрики скорости нужно читать в паре с качеством.** Рост скорости сам по себе ни о чём не говорит, если падает качество. Поэтому: долю влитого с первого прохода смотрим вместе с числом доработок. Частоту деплоев — вместе с **долей дефектов в проде и rollback-rate**. Ни одна метрика скорости не оценивается отдельно от парной метрики качества.

**Долю дефектов смотрим вместе с абсолютом.** Агент генерирует больше кода быстрее, поэтому абсолютное число дефектов может вырасти, даже если *доля* пойманного до merge улучшилась.

# Часть 8. Команда платформы ( операционная модель)

## 8.1 Задача команды

Команда платформы предоставляет продуктовым командам готовые компоненты, стандарты и контроли, которыми команды пользуются самостоятельно. Общие, кросс-командные skills, шаблоны и стандартные hooks. 
Продуктово-специфичные артефакты — контекст репозитория конкретного сервиса, hooks и промпты под его домен — пишут сами команды; платформа даёт каркас, примеры и ревью, но не пишет их за команду.

## 8.2 Зоны ответственности

1. **Доступ к моделям и харнесс** (L1/L2): API-доступ, слой абстракции, ключи, лимиты расходов, логирование. 
2. **Контрольный слой**: фреймворк hooks, permissions и sandbox, общие gate, защита веток.
3. **Eval-инфраструктура**: харнесс прогона evals в CI, golden-датасеты, регрессионные gate.
4. **Каркас знаний**: шаблоны intent/spec/plan/review, реестр skills, стандарты контекста репозитория.
5. **Наблюдаемость и стоимость (текущая AI-телеметрия)**: телеметрия AI-метрик и дашборды токенов/расходов в Prometheus/Grafana/Keep. Снятие baseline существующего процесса до старта — не здесь: это DevOps/observability + QA под accountability program-owner (§9.1).


## 8.3 Роли

Роли — это зоны ответственности, пока не  люди 1:1; на старте одну или несколько ролей может закрывать один человек. У каждой роли, помимо задач, зафиксированы **единоличная ответственность** и **граница** (чего роль не делает — как правило, не берёт на себя работу вместо команд).

**Program / Product owner платформы**
- Кто / занятость: part-time.
- Задачи: план и приоритеты (какой play и какая команда следующие); работа с заинтересованными сторонами — CTO, CPO, Team Leads, PO, отчёт CEO; освоение в командах и локальные эксперты; защита времени part-time людей; governance; baseline и метрики (**accountable**; снятие исполняют DevOps/observability + QA, не build-команда платформы).
- Единоличная ответственность: **темп и направление программы** — что внедряем, в каком порядке и почему это движется.
- Не делает: не пишет продуктово-специфичные артефакты за команды; не уходит в архитектуру харнесса.


**Platform Tech-lead**
- Кто / занятость: **выделенная ставка** (целевой профиль — platform / DevEx / DevOps). На старте роль закрывает человек из команды QA-агента (E2E Team), растущий в платформенную роль; в Фазе 0 — part-time, выделение на full time после результатов.  
- Задачи: архитектура харнесса и слоя абстракции L1/L2; стандарты hooks/evals/skills; ревью платформенного кода; снятие технических блокеров у участников;
отвечает за проработку всех стадий SDLC; 
- Единоличная ответственность: **работоспособность и единообразие платформенных компонентов и стандартов**.
- Не делает: общие skills, стандарты и hooks — держит, но продуктово-специфичные артефакты (контекст, hooks, промпты под конкретный сервис) команды пишут сами.
- **Ramp-план на 90 дней (= вклад в Фазу 0).** Человек известен (растёт из команды QA-агента, профиль platform/DevEx), поэтому это не наём, а раскладка задач по кварталу:
  - *Дни 1–30:* харнесс L1/L2 на opencode поднят, OpenSpec зафиксирован и развернут; каркас защиты веток и deny-правил.
  - *Дни 31–60:* стандарты hooks/evals/skills зафиксированы;  каркас продуктового пресета; решение build-vs-buy принято.
  - *Дни 61–90:* Build/Deploy проработаны на реальном образце; reverse-spec-образец на живом легаси проведён как **проверка жизнеспособности легаси-пути** (смог ли продукт дать вердикты по бизнес-вопросам агента: да → снятие легаси масштабируем; нет → запасной план); сквозной прогон на двух образцах пройден и замерен.

**Eval / Quality owner**
- Кто / занятость: из основателей QA-агента; part-time
- Задачи: golden-датасеты; определение «что такое хорошо»; регрессионные gate на изменения конфигурации агента; плейбуки стадий Design и Test.
- Единоличная ответственность: **измеримое качество** — данные, по которым принимается решение о расширении автономии.
- Не делает: не владеет инфраструктурой прогона evals (это Tech-lead); разделение намеренное — инфраструктуру держит один, содержание качества — другой.

**Platform / Agent engineer (×1–2)**
- Кто / занятость: early adopters и/или основатели QA-агента; part-time.
- Задачи: первые hooks и skills; слой абстракции и интеграция моделей; шаблоны контекста репозитория; интеграция в CI.
- Единоличная ответственность: **работающие платформенные компоненты** (hooks, skills, шаблоны), которыми пользуются команды.
- Не делает: не держит доменные знания в промптах агентов; не доводит агента до совершенства в ущерб внедрению.

**DevOps / CI (заимствованный)**
- Кто / занятость: из существующей DevOps-функции; part-time по запросу.
- Задачи: GitLab CI и Argo; защита веток; телеметрия в Prometheus/Grafana/Keep; **снятие baseline существующего процесса** (lead time, deploy frequency из GitLab/Argo), настройка rollback/hotfix-rate и логирования инцидентов.
- Единоличная ответственность: **пайплайн и технические gate** — что «агент только через MR» 
- Не делает: не строит харнесс (это ядро) — только сцепляет его с существующей инфраструктурой.

**Локальные эксперты в командах — вне численности платформы**
- Кто / занятость: по одному человеку в каждой продуктовой команде, part-time; остаются в своей команде, в штат платформы не входят.
- Задачи: онбординг своей команды, первая линия поддержки на месте, обратная связь платформе о том, что не работает.
- Единоличная ответственность: **освоение инструмента в своей команде**.
- Через них идёт масштабирование на Фазе 2: платформа обучает и поддерживает этих людей, а не обслуживает 15 команд напрямую.

## 8.4 Обязательные условия для состава

- **Accountable program-owner (part-time) + выделенная ставка Tech-lead.** Единый accountable program-owner (part-time, с защищённой долей времени) задаёт общий приоритет; выделенная ставка — у Platform Tech-lead. Без accountable-якоря part-time участники работают без общего приоритета, и программа теряет темп.
- **Защищённая доля времени у part-time участников**
- **Инженерная / платформенная глубина — ресурсный запрос №1.** Стартовое ядро — QA-происхождения (лидер направления, Tech-lead, участник из QA-агента),  стадии Build и Deploy остаются слабо проработанными. Закрываем инженерной ставкой (dev-контекст), которую ищем **среди текущих dev-кандидатов**, с part-time участием в Фазе 0 и выделением после результатов. 
- **Граница «не пишем за команды».** Спрос «сделайте нам hook или skill под наш сервис» появится в первый же квартал. Общий переиспользуемый компонент делает платформа; разовый продуктовый — команда, платформа даёт каркас и ревью. Иначе загрузка платформы растёт пропорционально числу команд.

# Часть 9. Фаза 0 и рамка роадмапа

Детально проработана только **Фаза 0 (Фундамент)** — она обязательна и одинакова под любой из трёх путей развития. Роадмап дальнейших фаз проектируется **после** выбора пути, поскольку зависит от него.

## 9.1 Фаза 0 — Фундамент 

 Ориентировочный горизонт Фазы 0 — TBD; состав в Фазе 0 весь part-time , поэтому **точную оценку объёма команда делает снизу вверх** на старте, а **организационный доступ запускаем сразу** (он календарно-зависим — закупка/юрформальности).

| Что строим | Выход |
|---|---|
| Организационный доступ + реестр разрешённых моделей | доступ выдан платформой, ключи под её управлением |
| Слой L1/L2/L3 на opencode; OpenSpec  | агент запускается, артефакты OpenSpec ведутся |
| reverse-spec скиллы (снять поведение / бизнес-вопросы); коннекторы к коду, TestIT, Confluence | агент читает три источника легаси |
| Политика использования AI и правила по данным; скан ПДн/секретов; защита веток | правила действуют, скан блокирует, `main` защищён |
| Каркас независимого приёмочного гейта (hook: приёмочные/смоук-тесты недоступны агенту-кодеру) | человеческая верификация защищена |
| Шаблоны intent/spec/plan/review; первые общие skills | команды берут готовое |
| Продуктовый пресет/скилл для OpenCode (интерфейс продукта) | продукт работает через CLI, не через git |
| Baseline существующего процесса (lead time, deploy frequency, время ревью, **доля дефектов в проде**) + настройка rollback/hotfix-rate и логирования инцидентов | снимают DevOps/observability + QA под accountability program-owner, параллельно, вне build-команды платформы |
| Назначен состав платформы: program-owner (part-time), Tech-lead (выделенная ставка), локальные эксперты | состав назначен (§8) |

**Сквозной прогон Фазы 0 — на двух образцах (измерительный эталон).** Прогон делается не на одной задаче, а на двух, потому что именно их дельта выбирает путь после Фазы 0 (§9.2):
1. **Greenfield-образное изменение** — новый сервис/фича полным циклом.
2. **Reverse-spec на живых (2–3) легаси-сервисах.**

По обоим замеряем: число обращений к модели и стоимость, время до принятой спеки, объём человеко-валидации. Дельта между образцами — первая реальная оценка стоимости и пропускной способности reverse-spec  и вход в выбор пути. Заодно Фаза 0 даёт **первую прикидку токен-экономики** (стоимость на смерженное изменение) — данные, которых сегодня нет.

**Reverse-spec-образец — не только замер, но и проверка «жив ли легаси-путь» (go/no-go): go = снятие легаси масштабируем вширь; no-go = включаем запасной план.** Весь transform держится на связке reverse-spec-скилла, валидации инженера и способности продукта выносить вердикты; скилл «перевести поведение в бизнес-вопрос» — ключевая (самая рискованная) точка этой цепочки (R-15). Критерий образца: **продукт реально смог вынести вердикты по сгенерированным бизнес-вопросам.** Если да — transform масштабируем; если вопросы вышли слишком техническими и продукт завис — включается запасной план (§3.8: сузить reverse-spec / оставить легаси ручным дольше), *до* раскатки вширь, а не после.

**Baseline — не задача build-команды платформы.** Его снимают существующие функции (DevOps/observability + QA) под accountability program-owner, параллельно Фазе 0. Платформа отвечает только за текущую AI-телеметрию (§8.2, зона 5).

**Критерий готовности Фазы 0:** политика разработана; baseline снят; сквозной прогон на двух образцах пройден и замерен.

## 9.2 После Фазы 0 — выбор пути

После Фазы 0 выбирается путь (G / T / параллель) — на данных. Если данные покажут стоимость на изменение выше ожидаемого порядка без пути снижения, пересматривается **дизайн** (объём внешнего API, класс задач агента, степень автономии), а не факт продолжения.

**Общее для всех вариантов:** Фаза 0 нужна под любой (предшественник, не часть развилки); baseline по 100+ сервисам — программа на кварталы, не пилот; узкое место при параллельности — продукт (~20), не инженеры (~130).

| Вариант | Суть | Что проверяет |
|---|---|---|
| **1. Greenfield-first** | 1–2 новых сервиса полным циклом | работает ли конвейер вглубь |
| **2. Transform-first** | снятие baseline легаси + наполнение контекста | масштабируется ли reverse-spec вширь |
| **3. Два трека** | greenfield + baseline одновременно | глубину и ширину ценой нагрузки на продукт |

**Рекомендация — greenfield-first как опенер:** не конкурирует за продукт (~20), даёт ранние данные по стоимости и lead time, не требует reverse-spec вширь. Это старт трансформации, не замена ей; момент расширения на легаси задаёт дельта стоимости из Фазы 0. Три варианта остаются на столе.

**Легаси идёт фоном.** Параллельно — небольшой пробный поток по легаси силами выделенной микрокоманды (reverse-spec-скилл, доменное знание, аналитик), под двумя ограждениями: (1) разворачивается только после go/no-go образца Фазы 0; (2) старт с некритичных сервисов. **Это не вариант 3:** greenfield — основной путь с полным ресурсом, а легаси-поток небольшой и включается только после go/no-go, поэтому за продукт не конкурирует. Ресурс микрокоманды — дополнительный, сверх платформенного ядра (в запрос к CEO).

**Роадмап под выбор:** **G** — пилот 1–2 продукта полным циклом (метрика — цикл idea→prod); **T** — стрим baseline + наполнение контекста (Jira/Confluence + вручную, §2.6; метрика — скорость/качество вширь); **два трека** — оба с обязательной проверкой горлышка на продукте (~20).

# Часть 10. Управление изменениями и переход людей

 Управление изменениями ведётся отдельным потоком, параллельным технической проработке.

## 10.1 Рамки изменений

- Изменения затрагивают не инструмент, а ежедневную работу на местах: инженер смещается от написания кода к постановке спек и верификации; продукт — от «требование = тикет» к владению спекой и вердиктам.
- Старт — с двух групп: продуктологи  и рядовые инженеры.

## 10.2 Ожидаемый эффект на людей

- Ожидается **микс**: перераспределение части людей в более ценную работу (спеки, верификация, платформенные skills/hooks, продуктовая аналитика) и рост эффективности с ** возможным частичным сокращением**. Это естественная динамика: часть сотрудников входит в новую модель, часть оказывается вне её.
- Решение «реинвестировать высвобожденную ёмкость в рост или изъять как сокращение» принимается позже, на данных — по аналогии с выбором пути.


## 10.3 Enablement продуктовых ролей

- **Учим не писать спеки, а проверять и утверждать их.** Черновик спеки пишет агент ; продукт объясняет словами, что нужно, проверяет результат и утверждает. Формальному синтаксису требований (EARS) продукт не учится — обучение про суждение и приёмку.
- **Работают внутри OpenCode, без git и терминала.** Не отдельная программа, а «продуктовый режим» (пресет/скилл) в OpenCode: он задаёт вопросы аналитика (интервью Plan), сам оформляет `intent.md`/`spec.md`, делает commit и открывает MR, а продукту показывает спеку человеческим языком на утверждение. Git и терминал скрыт. Сам пресет — пункт чек-листа Фазы 0.
- **Сначала проверяем на 2–3 продуктологах**, потом раскатываем на всю группу.
- **Сложность вводим в два шага (в связке с greenfield-first):** сначала лёгкое — проверить спеку под новую фичу (свежий `intent`); потом тяжёлое — вердикты по легаси («старое правило оставить, выкинуть или изменить?»), уже с transform-фазой.

## 10.4 Enablement инженеров (DEV + QA)

- Переход роли: от «писателя кода» к автору спек и планов, верификатору и автору skills/hooks. Верификация — инженерная дисциплина (суждение, оценка рисков, проектирование проверок), а не механическая рутина ревью.
- Опора на существующие победы: работающий QA-агент и его создателей, прорывы в MS Team — первые носители практики и могут быть наставниками.
- **Фаза погружения** на личных учётных записях (квартал, параллельно Фазе 0): освоение агентной работы на своих задачах при жёстком правиле «данные клиентов, секреты, репозитории ограниченного доступа — никогда». Регулируется манифестом использования (отдельный документ). Успех фазы меряется способностью и безопасностью, не пропускной способностью.
- **Про джунов.** Агент пишет простой код, на котором джуны росли, —  путь роста исчезает, а джун, не умеющий судить вывод, его штампует (риск и для роста в  будущих сеньоров, и для контура верификации). Правило: джуны намеренно продолжают часть работы делать руками (формирование навыка), а рост джунов — зона ответственности тимлидов.
- **QA (в продуктовых командах и SDET) → владение верификацией с человеческой реализацией.** Агент-кодер пишет код и юнит-тесты (самопроверка), но **не все слои проверки отдаём LLM.** Критический смоук/приёмочный слой **пишет и поддерживает AQA — руками, без агента и недоступно ему** (hook): это независимый слой. LLM-сгенерированные приёмочные проверки из Given/When/Then (§3.3) добавляют охват **поверх** человеческого слоя, не вместо. Плюс ручное исследовательское тестирование. Всё это — часть gate 

## 10.5 Механика поддержки

- **Локальные эксперты** в каждой команде — первая линия и канал обратной связи; через них идёт масштабирование, платформа не обслуживает 15 команд напрямую.
- **Общая библиотека шаблонов и skills** — переиспользуемые паттерны; растёт в том числе из фазы погружения.
- Правило **«агент ошибся дважды → правка в контекст репозитория или skill»**.
- **Еженедельный разбор** допущений и открытых вопросов из артефактов как перечень пробелов в контексте.
- **Приглашённые эксперты с рынка**

## 10.6 Метрики адопшна

Меряют освоение, а не пропускную способность.
- **Охват:** доля целевой популяции по ролям, прошедших практический чекпоинт (реальный цикл `plan→spec→build→verify`, не демо).
- **Реальное использование:** доля изменений/фич, прошедших через новый конвейер, а не в обход.
- **Трение** (качественный сигнал): где люди застревают — для калибровки поддержки.

## 10.7 Процессные ритуалы

Меняются не только артефакты, но и церемонии, которые команды чувствуют ежедневно:

- **Refinement и оценка** смещаются: обсуждение уходит в `intent`/спеку с агентом, а не в устные оценки задач.
- **Definition of Done** включает верификацию (вывод самопроверки) и трассируемость (требование → тест → код).
- **Авторизация прод-релиза** — новая точка процесса (не новая ставка): прод-деплой авторизует назначенный владелец — функция на существующем владельце кода/тимлиде (gate-hook «спросить»).
- **Инцидент → eval:** прод-инцидент, вызванный работой агента, превращается в постоянный eval; закреплённая ответственность за это — часть процесса, а не разовое действие.
- **Jira** из хранилища требований становится трекером задач  — существующие workflow перестраиваются  под это.
- **Планирование и иерархия работ (PI Planning, PBV/ABV, Jira-иерархия, оценка)** — на перестройку отдельным потоком (§10.8).

## 10.8 Перестройка производственного процесса 

Меняются не только артефакты и церемонии, но и сам производственный процесс — ритм планирования (PI Planning, PBV/ABV), иерархия работ в Jira, оценка. Это отдельный поток со своим владельцем.

- **Роль — Agile Lead.** Мандат: **проанализировать, предложить и внедрить** новый производственный процесс. SAFe-образные артефакты и ритуалы — на пересмотр вплоть до отказа, если не служат новой модели.
- **Представители в потоке:** по одному от PO и аналитиков.
- **Граница ролей:** платформа (Tech-lead) строит **механизм** (харнесс, hooks, evals, гейты); Agile Lead перестраивает **ритм** (ритм, поток работ, DoD, RACI новых точек процесса — авторизация релиза; интеграция межсервисной фичи на команде оркестратора); технические стадии Build/Deploy остаются за Tech-lead; направление и приоритет — за program-owner.
- **Рамки перестройки:**
  1. *Упростить процесс, а не отменить его.* Убираем то, что держалось на медленной разработке (story points, velocity-оценки); сохраняем кросс-командную координацию, приоритизацию, управление зависимостями и планирование ценности (PBV/ABV).
  2. *Церемонии и ритмы меняем свободно, но принятые решения методики не переоткрываем:* спека — истина требований , два гейта , Jira — трекер, верификация раньше приёмки, автономия по метрикам ).

# Часть 11. Открытые вопросы и TBD

1. **Выбор LLM отложен намеренно.** Методика вендор-нейтральна , поэтому конкретная модель и провайдер выбираются позже  До выбора фиксируется только требование: организационный доступ с зоной хранения и без обучения на наших данных.
2. **Стоимость обращений к модели**  — модель расчёта и лимиты расходов; данных пока нет.
3. **Границы допустимого для внешнего API** — какие именно репозитории, US и proto можно отправлять, а какие нет (классификация репозиториев).
4. **Перевод продукта на модель «требование живёт в спеке, а не в тикете»** — задача трансформации: все сотрудников привыкли, что требование = тикет. Нужны обёртка над репозиторием, примеры и онбординг.

## Приложение G. Глоссарий

- **Артефакт-цепочка** — последовательность версионируемых файлов (intent → spec → tasks → diff → PR), одновременно передача между стадиями и аудиторский след.
- **Продукт (продуктологи)** — группа продуктовых сотрудников (PO, PM, бизнес-аналитики, ~20 человек), владелец бизнес-требований (`proposal` + `specs`) и Гейта 1 (бизнес-приёмка). Не путать с «сервисом/продуктом» как ПО и с «продуктовым контекстом» (§2.6).
- **EARS** — Easy Approach to Requirements Syntax; фиксированные формы атомарных требований.
- **Evals (оценочный набор)** — набор реальных задач с принятым исходом, оформленных как проверки (тесты зелёные, линтер чист, поведение не изменилось, политика соблюдена). Гоняется в CI по расписанию и на любое изменение конфигурации агента (контекст, skills, hooks) — регрессия на самого агента, как тесты на код. Изменение, роняющее pass-rate, ревьюится до merge; каждый прод-инцидент превращается в постоянный eval (§4.4).
- **Hook** — детерминированная проверка на действие агента: пропустить / спросить / заблокировать.
- **Продуктовый (доменный) контекст** — сквозное доменное знание (термины, статусные модели, типы клиентов, интеграции), не привязанное к одному сервису; отдельно от baseline легаси (§2.6, §3.8).
- **Skill** — версионируемое обязательное правило или процедура организации, применяется агентом по описанию.
- **Контур самопроверки** — способ агента проверить свою работу до человека (тесты, сборка, скриншот).
- **Gate** — точка, где продолжение требует утверждения человеком.
- **Защита веток** — настройки, не дающие смержить в защищённую ветку без выполнения условий (аппрув, зелёный pipeline, запрет прямого push).
- **CODEOWNERS** — файл-механизм в репозитории (GitLab/GitHub), сопоставляющий **пути файлов → их владельцам** (людям/командам). MR, затронувший эти пути, автоматически запрашивает ревью у владельцев; с защитой веток их аппрув обязателен для merge. Это **не роль доступа GitLab** (Owner / Maintainer / Developer), а маршрутизация ревью по пути файла — так гейты попадают к ответственным (§3.5, §4.5).
- **Доля автономных действий** — доля действий агента, прошедших за gate без ручного касания.
- **Обращение к модели (inference)** — один запрос к LLM и её ответ (вход → выход). Тарифицируется по объёму текста (токенам). Модель при этом не обучается, а только используется. На одну задачу агент делает много обращений подряд, поэтому стоимость одной задачи складывается из десятков-сотен таких вызовов.
- **Токен** — минимальный кусочек текста, которым модель считает вход и выход; по числу токенов провайдер выставляет счёт.

```markdown
| number-lifecycle.md  | Статусная модель номера (Active/Blocked/…) и переходы        | статусы, смена состояний |
| number-attributes.md | Атрибуты номера (call_record, speech_analytics, amd…): смысл, кто включает | поля GetAttributes, флаги функций |
| billing-rules.md     | Правила тарификации                                          | биллинг, стоимость, тарифы |
| voice-rules.md       | Голосовые вызовы и запись разговоров                         | звонки, запись, транскрибация |

Факт без источника в файлы не попадает; каждый доменный файл — с frontmatter (name/description/updated/owner).
```

**H.2 Корневой `CONTEXT.md` репозитория сервиса** (всегда загружается, ≤1 стр.):

```markdown
# Repo context
## Сборка и тесты
- Сборка: `make build` · Тесты: `make test` (ненулевой код при провале) · Линт: `make lint`
## Конвенции
- JSON: snake_case; URL: kebab-case; ошибки — RFC 7807
- proto — истина контракта; спека — поведение
## Архитектура (кратко)
- gRPC-сервис; API — `api/`, логика — `internal/`; общие контракты (proto) — в репо `contracts/`
## Грабли
- Не звать чужие сервисы напрямую — через клиент, сгенерированный из `contracts/`
## Где искать больше (грузить по месту, не дублировать сюда)
- Локальный контекст модуля — `internal/<module>/CONTEXT.md` · ADR — `docs/adr/` · раннбуки — `docs/runbooks/`
- Общие контракты — репо `contracts/` · доменные факты — репо `product-context/INDEX.md`
```

**H.3 Локальный `CONTEXT.md` модуля** (напр. `billing-service/internal/charging/CONTEXT.md`, индексируется по локальности):

```markdown
# Context: charging module
## Особенности
- Идемпотентность списаний по `idempotency_key`; суммы — в минимальных единицах (копейки)
## Тесты
- `make test-charging`; фикстуры — только синтетика
## Грабли
- Не менять `contracts/billing.proto` без версии — контракт публичный
```

**H.4 Где что лежит — раскладка в polyrepo.** Требования, код и контекст — **три разные вещи с разной ролью** (подробнее — §3.12). Раскладка — polyrepo: сервис = отдельный репозиторий группы GitLab, `openspec/` в каждом.

```
git.<...>/<группа>/                ← группа GitLab, сервис = отдельный репозиторий
│
├── billing-service/               ← репозиторий сервиса
│   ├── openspec/
│   │   ├── specs/                 ← ИСТИНА ТРЕБОВАНИЙ сервиса («что делает»)
│   │   │   └── spec.md            ←   as-is baseline легаси (§3.8): поведения
│   │   │                              (EARS+GWT) + уверенность + вердикты продукта
│   │   └── changes/
│   │       └── 2026-add-call-record/   ← изменение «в полёте»
│   │           ├── proposal.md          бизнес (продукт, гейт 1)
│   │           ├── specs/               дельта требований
│   │           ├── design.md            техника (инженер, гейт 2)
│   │           └── tasks.md             нарезка + «План реализации» (§4.3)
│   │                                    (принятое → мержится в specs/ → архив, §3.2)
│   ├── api/  internal/            ← КОД сервиса
│   └── CONTEXT.md                 ← подсказки агенту по локальности (H.3), НЕ требования
│
├── numbers-service/   …           ← аналогично, свой openspec/          × 100+
│
├── contracts/                     ← общие proto (истина контракта межсервисных изменений, §3.11)
└── product-context/               ← сквозное доменное знание + INDEX.md (H.1)

TestIT (вне git) ─── кейсы с тегом R-id (<сервис>/R-n); связь с кодом по номеру TC (§3.9)
```

- **Спека ≠ код ≠ контекст.** Спека (требования) — в `openspec/specs/` репозитория сервиса; код — там же; контракт — в `contracts/`; контекст (`CONTEXT.md`, `product-context/`) — подсказки агенту, не истина. As-is baseline легаси — это **спека**, лежит в `openspec/specs/` своего сервиса.
- **Polyrepo:** `openspec/` — в каждом репозитории сервиса; общие proto и `product-context/` — отдельными репозиториями группы. R-id неймспейсится префиксом сервиса (`<сервис>/R-n`), т.к. TestIT один на группу. Подробнее — §3.12.
