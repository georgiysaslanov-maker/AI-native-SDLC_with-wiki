# Вендор-нейтральная агентная архитектура (L1/L2/L3)

> Трёхуровневый слой абстракции — модель, харнесс, роли агентов — позволяющий менять провайдера модели и инструмент без переписывания ролей и контрактов.

## Содержание

| Уровень | Что это | Свойства |
|---|---|---|
| **L3. Роли агентов** | orchestrator · spec · coder · reviewer · … | контракты «кто за что отвечает и чем ограничен»; не зависят от модели и харнесса |
| **L2. Харнесс** | opencode / собственный оркестратор / Claude Code | сменяемый; единый интерфейс prompt, tools, hooks, permissions, logs |
| **L1. Модель** | внешний API (Enterprise-решение) | сменяемая, выбирается под задачу; к контрактам и evals не привязана |

### Роли агентов (минимальный набор)
| Роль | Стадии | Что делает | Ограничение |
|---|---|---|---|
| orchestrator | все | маршрутизирует задачу, вызывает роли | не пишет в базу знаний, знаниями не владеет |
| spec | Plan, Design | intent → `spec.md` (EARS), ищет неопределённости и противоречия, читает `product-context/` | формулирует открытые вопросы, но не отвечает на них сам |
| coder | Build | пишет код и тесты по `tasks.md` | не мержит; не трогает защищённые пути (hook) |
| reviewer | Test, Deploy | ревьюит PR против `REVIEW.md`, сверяет со spec и tasks | его находки не утверждают PR |

Файлы ролей содержат только роль и маршрутизацию, а не доменные факты.

### Шлюз на границе L2↔L1
- Идентичность — на человека (корпоративный SSO); сырой API-ключ разработчику не выдаётся.
- Ключи — пул из ~3–6 штук по границам риска: интерактивная разработка, CI по окружениям, служебный ключ для батч-агентов.
- Шлюз — единая точка kill-switch и токен-бюджетов.

### Зачем
Снижает зависимость от вендора (R-08) и риск блокировки аккаунта (R-14): провайдера можно сменить без переписывания ролей.
