# Контекст репозитория (AGENTS.md / CONTEXT.md)

> Файл правил и подсказок агенту в корне репозитория (аналог `CLAUDE.md` / `AGENTS.md`): конвенции, команды сборки и тестов, архитектура, грабли; ревьюится как код.

## Содержание

### В методике
- Один файл в корне репозитория, до одной страницы, читается в начале сессии; ревьюится как код.
- Плюс локальные `CONTEXT.md` по модулям/сервисам — грузятся по месту работы (индексация по локальности).
- Пример корневого `CONTEXT.md`: сборка/тесты/линт (`make build`, `make test` с ненулевым кодом при провале), конвенции (JSON snake_case, URL kebab-case, ошибки RFC 7807, «proto — истина контракта; спека — поведение»), краткая архитектура, грабли, ссылки «где искать больше» (ADR, раннбуки, `contracts/`, `product-context/INDEX.md`).
- `CONTEXT.md` — подсказки агенту, **не** требования и не истина.
- Пишут сами команды; платформа даёт каркас, примеры и ревью. Риск R-18 — по 100+ репозиториям контекст будет отставать.
- Правило «повторное замечание на ревью → в контекст/правила репозитория»; «агент ошибся дважды → правка в контекст или skill».
- В Test: пример корректного вывода `make test` описывается в контексте репозитория.

### На митапе
- И. Румянцев: в pet-проекте ~90% контекста жило в трёх файлах — ТЗ (с ключевым правилом «чего нет в ТЗ — не выдумывай, спроси»), пять ADR и жёсткие правила для агента (`AGENTS.md`): источник истины — ТЗ, обязательное соблюдение ADR, обязательные команды, «секреты никогда не храним в env», тесты всегда, эндпоинты Exolve сверять с публичной документацией и не выдумывать параметры, план вех и критерии готовности вехи. `AGENTS.md` написан вместе с агентом; агент читает его по умолчанию.
- Архитектурные решения хранятся в ADR и служат контекстом агента вместо «знаний в головах».
- Г. Лебедев: `AGENTS.md` — правила работы с проектом, часть харнесса.
