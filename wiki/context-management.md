# Управление контекстом агента

> Контекстное окно — ограниченный ресурс: знания загружаются точечно (just-in-time), а не «всё всем»; раздутый контекст ухудшает результат и стоит токенов.

## Содержание

### Принцип методики
- Принцип 4: «Контекст — ограниченный ресурс». Знания грузятся just-in-time.
- Два слоя знаний масштабируются по-разному:

| | Продуктовый контекст | Контекст репозитория |
|---|---|---|
| Содержит | сквозные доменные факты | конвенции, команды, архитектура, грабли |
| Индексируется | по релевантности (`INDEX.md`, 1–3 файла под задачу) | по локальности (файловая иерархия) |
| Форма | библиотека доменных файлов + `INDEX.md` | корневой one-pager + локальные `CONTEXT.md` |

- С ростом системы растёт общее знание, но не всегда-загружаемый файл: рост уходит в декомпозированные слои, корневой контекст остаётся тонким.
- Антипаттерн: раздутый контекст репозитория — релевантное теряется среди устаревшего.

### На митапе (А. Захватов)
- Контекстные окна растут (32K, 64K, …), но есть **usable context window** — полезный бюджет модели. Плохая идея — грузить 20 страниц вики или весь репозиторий «найди проблемы».
- Практический ориентир докладчика: не держать заполненными больше ~150 тыс. токенов.
- Со ссылкой на доклад создателя фреймворка BMAD: при заполнении окна на 50% шанс, что модель «вспомнит» токен из начала, — 6–8%.
- Цитата представителей Anthropic (2025): ищите минимальный набор токенов, дающий агенту то, что нужно → спецификация должна быть максимально короткой.
- Г. Лебедев: харнесс собирается под задачу, чтобы не перегружать окно; в skill важное ставится в конец, т.к. агент лучше удерживает последние токены.
- Реплика из зала: при переполнении контекста нужно делать компактизацию сессии.
