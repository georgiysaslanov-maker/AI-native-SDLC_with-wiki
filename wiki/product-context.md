# Продуктовый (доменный) контекст

> Сквозное доменное знание (термины, типы клиентов, статусные модели, интеграции, тарификация), не привязанное к одному сервису; агент читает его, чтобы не галлюцинировать бизнес-факты.

## Содержание

- **Расположение:** отдельный репозиторий `product-context/` в группе GitLab.
- **Структура:** `INDEX.md` (однострочные описания файлов + «читать, когда задача про…») + доменные файлы, нарезанные по потребностям агентов, а не по структуре вики: `glossary.md`, `client-types.md`, `number-lifecycle.md`, `number-attributes.md`, `billing-rules.md`, `voice-rules.md` и т.п.
- **Формат файла:** frontmatter (`name`, `description`, `updated`, `owner`) + факты с обязательным источником (US, Confluence, подтверждение эксперта). Факт без источника в файл не попадает.
- **Загрузка:** прогрессивная — агент читает `INDEX.md` и выбирает 1–3 релевантных файла.
- **Наполнение (по порядку):** 1) Jira разово — факты из истории US с `source: EXOLVE-XXX`; 2) Confluence разово — с пометкой «задокументированное намерение, не проверенное поведение»; 3) ручное закрытие пробелов через интервью с агентом. Продукт валидирует черновик целиком, затем коммит.
- На greenfield-пути и в Фазе 0 стартует **тонким** (глоссарий + нужное пилоту); полный скан Jira/Confluence — вместе с transform-путём.
- **Пополнение:** новые факты из принятых спек и закрытых открытых вопросов `intent.md`/`spec.md` выносятся в слой.
- **Владелец:** продукт/аналитик; изменение — обычным MR.
- Отличается от baseline легаси (поведение одного сервиса) — тот живёт в `openspec/specs/` сервиса.
- Риск R-18: источники устарели/неполны, наполнение конкурирует за дефицитный продукт.
