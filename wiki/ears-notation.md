# EARS и Given/When/Then

> Нотация требований в методике: EARS — для атомарных требований с обязательным источником, Given/When/Then — для исполняемых критериев приёмки.

## Содержание

- **EARS** (Easy Approach to Requirements Syntax) — одно атомарное предложение фиксированной формы с обязательным `source:`. Атомарность даёт правило «одно требование = минимум один тест» и машинно-разбираемые идентификаторы (R-id).
- Формы EARS из шаблона `spec.md`:
  - `[Ubiquitous]` СИСТЕМА ДОЛЖНА {инвариант}.
  - `[Event-driven]` КОГДА {событие}, СИСТЕМА ДОЛЖНА {реакция}.
  - `[State-driven]` ПОКА {состояние}, СИСТЕМА ДОЛЖНА {ограничение}.
  - `[Unwanted]` ЕСЛИ {ошибка}, ТО СИСТЕМА ДОЛЖНА {отказ + код}.
- **Given/When/Then** — критерий приёмки на каждое требование (`AC-n (R-m)`).
- Бизнес-слой: EARS + GWT, много примеров; технический слой: EARS строже + ссылки на proto.
- Требование без `source` не принимается.
- R-id в polyrepo неймспейсится префиксом сервиса: `<сервис>/R-<n>` (TestIT один на группу).
- Продукт синтаксису EARS **не учится**: черновик пишет агент, обучение продукта — про суждение и приёмку.

**Пример минимальной спеки (из методики):** R-1 [Event-driven]: КОГДА вызван `POST /number/v1/GetAttributes` с валидным `number_code`, СИСТЕМА ДОЛЖНА вернуть в `attributes` булево поле `call_record` (source: proposal); AC-1/AC-2 — запись разговоров выключена/включена → `call_record = false/true`.

Шаблон `spec.md` также содержит разделы «Противоречия источников (US ↔ proto)» и «Открытые вопросы (блокируют утверждение)».
