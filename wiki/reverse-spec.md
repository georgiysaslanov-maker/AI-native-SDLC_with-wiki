# Reverse-spec (baseline легаси)

> Поток SDD для легаси: прежде чем агент меняет код, поведение которого нигде не описано, снимается спека «как есть» (baseline) из кода, тестов и Confluence, валидируемая инженером и продуктом.

## Содержание

- **Источники и приоритет:** код (что система фактически делает — высший) > тест-кейсы (как тестировали — средний) > Confluence (задокументированное намерение — низший). Агенту подаётся только пространство Confluence нужного сервиса.
- Флагами поднимаются все расхождения: код↔тесты, код↔Confluence, Confluence↔тесты. Ценность Confluence — вскрывать расхождение поведения с намерением.
- **Уровни уверенности:** высокая (код + тест) — беглое внимание; средняя (только код) — обязательное; низкая (источники противоречат) — приоритетное.
- **Цепочка:** reverse-spec агент → черновик baseline с пометками → инженер валидирует (фокус на среднем/низком доверии) → агент переформулирует каждое правило в **бизнес-вопрос** («система при X делает Y — намеренное правило, баг или устаревшее?») → продукт выносит вердикты → baseline ложится в `openspec/specs/<сервис>/`.
- Глубина продуктовой валидации — по классу критичности: биллинг, тарификация, тайна связи — по каждому правилу; внутренние сервисы — выборочно.
- На старте один агент с двумя скиллами: «снять поведение» и «перевести поведение в бизнес-вопросы». Второй — самая рискованная точка (R-15).
- **Go/no-go** на образце Фазы 0: смог ли продукт вынести вердикты. No-go → запасной план: сузить reverse-spec или осознанно оставить легаси ручным дольше.
- Вердикт «документация устарела» порождает задачу владельцу сервиса на обновление Confluence.
- Антипаттерны: инженер подтверждает baseline целиком; продукту показывают техописание вместо бизнес-вопроса; три источника слиты в гладкую спеку.
